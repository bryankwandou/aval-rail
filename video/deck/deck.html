The problem

A Solana blockhash lasts about ninety seconds.

Put a human approval in front of an agent's payment and the transaction is dead before anyone answers. The owner is serving a table. The transaction is garbage.

This is why agent-payment designs quietly drop the human. The gate isn't removed because it's unwanted — it's removed because it doesn't survive contact with a blockhash.

$ solana confirm -v 4kR8...control
  Result: Error
  Hash has expired
The primitive

A durable nonce replaces the blockhash with an account.

The transaction stays valid until the nonce advances. Build it now, approve it whenever, submit it then. The nonce advances on use, which closes replay.

The product

The till is the chat window the owner never closes.

"Charge table 4, 25 USDC." The agent turns that into a Solana Pay request the customer settles from any wallet, watches the chain for it, and prepares refunds for the owner to approve.

charge-request

One sentence in, one payment request out. Three steps.

settlement-poll

Heartbeat, every five minutes. Asks the chain, not the customer.

refund-approval

Two independent human gates. An unanswered prompt denies.

Where the safety actually lives

The limits are not in the prompt.

The ceiling and the allowlist are read from the operator's config inside the sandbox and enforced in Rust. They are not arguments the model can pass, so no message arriving in the shop can raise one.

permissions = ["config_read"]        # no http_client, at all

"additionalProperties": false        # no recipient field to supply

Custody

The charge path holds no key and signs nothing.

A transfer request is a string and a hash. The customer's own wallet builds and signs the transaction. Tier T0 — there is no key to lose, because there is no key.

  • T0 · charging. No key, no signature, no submission. The component has no network permission and could not reach an RPC endpoint if asked.
  • T1 · refunds. The agent builds an unsigned, nonce-anchored transaction. A human signs it. The destination is read from the transaction that paid the order, never from a message.
The test the model failed

What held was structure, not judgement.

An injected message asked for a refund to a different address, phrased like ordinary business. The model did not refuse it. It fabricated a tool result that looked like success.

native_tool_calls: 0      parsed_tool_calls: 0

no tool ran · no key exists · destination is read from the chain

The model failed this test. The system did not.

What I'd tell the next builder

Five settings that start the daemon and do nothing.

  • schema_version missing — discards the entire provider block, silently.
  • [channels.telegram] instead of the dotted form — binds nothing.
  • execution_mode — the key is default_execution_mode; the wrong one is accepted and ignored.
  • deterministic mode — runs headless with no agent turn; ordinary steps fail closed.
  • WIT drift — one enum variant apart, compiles and installs, fails only at instantiation.
Check retained, not policy_allowed. A tool name that doesn't match is dropped without a word.
